## Загальне

### Що робить цей фільтр?

Він розташовується між GNSS-приймачем і контролером польоту. Фільтр у
реальному часі моніторить якість GPS і блокує передачу GNSS-даних на FC,
коли виявляє аномалії — спуфінг, глушіння або втрату сигналу. FC тоді
переходить на dead-reckoning (інерційну навігацію), поки не повернеться
чистий GPS-сигнал. Див. [Огляд пристрою](#device-overview) для детального пояснення.

### Які контролери польоту підтримуються?

Будь-який FC на базі ArduPilot з версією **ArduPilot 4.6.1 або новішою** (Copter, Plane,
Rover). F401 і H743 UART-збірки комунікують через стандартну MAVLink2-телеметрію
та FC GPS UART. H743 DroneCAN-збірка публікує native DroneCAN GPS і не має
фізичних FC serial ports. Натомість `v0.2.0+` передає OpenIPC camera MAVLink2
через S1/index `0`, а MAVLink2 фільтра та зворотну FC telemetry — через
S2/index `1`.

H743 DroneCAN `v0.5.30+` явно запитує `AUTOPILOT_VERSION` і fail-closed, якщо
FC не відповідає або повідомляє версію старішу за 4.6.1: `Fix2/Auxiliary`
припиняються негайно. 15-секундний grace period затримує лише `FC VERSION
UNKNOWN` / `AUTOPILOT_VERSION REQUIRED` (або `FIRMWARE TOO OLD` / `UPDATE TO
ARDUPILOT 4.6.1+`) та hard fault processing; він ніколи не дозволяє GPS, доки
identity невідома або непідтримувана.

### Які GNSS-приймачі працюють?

- **u-blox**: сімейства M8, M9, M10, F9, F10 (`GNSS_TYPE=0`)
- **Unicore**: UM980, UM981, UM982 (`GNSS_TYPE=1`) — потребує одноразового налаштування, див. [Конфігурація приймача](#receiver-config)
- **Septentrio**: Mosaic X5 (`GNSS_TYPE=2`) — H743 DroneCAN може використовувати SBF; UART-збірки використовують NMEA, див. [Конфігурація приймача](#receiver-config)

### Чи можна використовувати з PX4 або iNav?

Наразі ні. MAVLink/DroneCAN інтеграція фільтра розроблена для ArduPilot.

### Від яких систем РЕБ захищає?

Захист визначається аномаліями, які може спостерігати конкретна установка:
стрибками позиції, патернами SNR, розходженням висоти та зменшенням кількості
супутників. Фільтр не ідентифікує модель обладнання РЕБ і не може гарантувати
виявлення кожної поточної чи майбутньої атаки. Результат залежить від приймача,
антени, монтажу, профілю налаштувань і самого сценарію впливу.

**Класи загроз, які враховувалися під час розроблення:**

- **Українські:** Ліма, Пательня, Покрова (GPS спуфінг); Буковель, Нота, Дамба, Анклав (глушіння GNSS); Кульбаба, PARASOL, Піранья AVD 360 (придушення дронів)
- **Російські:** Поле-21/Field-21, Шипівник-Аеро (GPS спуфінг); Р-330Ж Житель (глушіння+спуфінг GNSS); Красуха-2/4 (глушіння радарів); Борисоглібськ-2, Леєр-3, Мурманськ-БН, Палантин (глушіння зв'язку); Репеллент-1, Інфауна (придушення дронів/СВП)
- **Білоруські:** Гроза (глушіння GNSS)

Цей перелік є довідковою картою загроз, а не заявою про контрольоване
випробування проти кожної названої системи. Див. [Огляд пристрою](#device-overview)
та виконайте [лабораторний чекліст](../08_lab_validation.md) на фактичній
комбінації приймача, польотного контролера і монтажу перед польотом.

## Апаратне забезпечення

### Яка плата потрібна?

STM32F401CC BlackPill V2.0 (WeAct Studio) для основної UART-версії. Для H743
DroneCAN потрібна WeAct Studio MiniSTM32H743VITX і 3.3 V CAN transceiver,
наприклад SN65HVD230; повний wiring/flash шлях описаний у
[H743 DroneCAN Guide](13_h743_dronecan.md). Можна [придбати готову плату](https://airdroper.org/products/gps-spoofing-filter) або прошити самостійно — див. [Самостійна установка](#self-install).

### Чи можна використати іншу плату STM32?

Тільки підтримувані target-и. Прошивка скомпільована під конкретну розпіновку
та карту пам'яті: F401 BlackPill, WeAct H743 standalone UART або WeAct H743
DroneCAN. Інші STM32-плати потребують окремого board target.

### Чи підтримує H743 CAN напряму?

STM32H743 має FDCAN peripheral, але його `PB8/PB9` - це logic-level TX/RX, не
CANH/CANL. Для підключення до flight controller CAN port потрібен зовнішній
3.3 V CAN transceiver, наприклад SN65HVD230. Підключення напряму без
transceiver не працюватиме.

### Які швидкості передачі використовуються?

| Канал | Швидкість |
|-------|-----------|
| GNSS ↔ STM32 | 460800 (за замовчуванням, автовизначення) |
| FC MAVLink ↔ STM32 | 115200 |
| FC GPS ← STM32 | 460800 |
| OpenIPC camera ↔ H743 | 115200 (3.3 V MAVLink2 UART) |
| H743 DroneCAN S1/S2 virtual ports | 115200 metadata (`BD=115`) |
| H743 DroneCAN CAN bus | 1000000 |

### Чи потрібно окреме живлення для STM32?

F401 отримує живлення від FC/SWD; не підключайте BlackPill USB-C. WeAct H743
можна живити/flash через USB-C для bench/ROM DFU, але CAN/GNSS/FC wiring все
одно має мати спільну землю. Див. [Схема підключення](#wiring) і
[H743 DroneCAN Guide](13_h743_dronecan.md).

## Налаштування

### FC показує "No GPS" або "GPS: not healthy"

1. Перевірте підключення — TX і RX мають бути перехрещені (див. [Схема підключення](#wiring))
2. Переконайтесь, що `SERIAL_BAUD` відповідає (460800 для GPS UART, 115200 для MAVLink)
3. Тимчасово встановіть `FCGPS_FWD=1`, щоб примусово увімкнути FC GPS UART і сиро пересилати GPS на FC навіть до прийняття фікса фільтром. Перед польотом поверніть `0`.
4. Для UM980 або Mosaic X5: переконайтесь, що приймач попередньо налаштований і ArduPilot не переписує цей профіль (див. [Конфігурація приймача](#receiver-config))

Для H743 DroneCAN замість UART bypass перевірте, що node ID `42` видно у
DroneCAN/SLCAN tooling, FC CAN port має `CAN_Dx_PROTOCOL=1`, bitrate
`1000000`, а GPS instance має `GPS1_TYPE=9`. Якщо GPS працює, але camera або
filter MAVLink відсутній, також перевірте `CAN_Dx_UC_SER_EN=1`, S1 node
`42`/index `0`/baud `115`/protocol `2` і S2 node `42`/index `1`/baud
`115`/protocol `2`.

Якщо проблема залишається, див. [Діагностика підключення](#wiring-debug) для покрокового усунення несправностей.

### Як дізнатись, який GNSS_TYPE використовувати?

- Якщо ваш приймач u-blox (NEO-M8, NEO-M9, ZED-F9P тощо): `GNSS_TYPE=0`
- Якщо ваш приймач Unicore UM980, UM981 або UM982: `GNSS_TYPE=1`
- Якщо ваш приймач Septentrio Mosaic X5: `GNSS_TYPE=2`. Використовуйте SBF profile на H743 DroneCAN; використовуйте NMEA на UART-збірках.

Див. [Налаштування та прошивка](04_setup_and_flash.md) для зміни цього параметра.

### Чи потрібно налаштовувати приймач UM980?

Так. STM32 **не** виконує автоконфігурацію UM980. Вам потрібно застосувати
профіль конфігурації через UPrecise перед першим польотом. Див.
[Конфігурація приймача](#receiver-config) для точних команд.

### Чи потрібно налаштовувати приймач Mosaic X5?

Так. STM32 **не** виконує автоконфігурацію Mosaic X5. Налаштуйте приймач через
Septentrio RxTools/Web UI. Для H743 DroneCAN увімкніть SBF profile
(`PVTGeodetic`, `DOP`, `ReceiverTime`, `MeasEpoch`, `PosCovGeodetic`,
`VelCovGeodetic`) на послідовному потоці, підключеному до STM32. Для
UART-збірок увімкніть NMEA `GGA`, `RMC`, `GSA`, `GSV` і `VTG`. Потім збережіть
профіль у boot.

### Чи потрібно налаштовувати приймач u-blox?

Ні. STM32 автоматично налаштовує u-blox приймачі при завантаженні. Просто підключіть.

## Робота

### Що таке DR0 і DR1?

- **DR0** = штатний режим. GPS-дані передаються на контролер польоту.
- **DR1** = захисний режим. GPS-дані заблоковані. FC використовує dead-reckoning.

Див. [Огляд пристрою](#device-overview) для детального пояснення.

### Як швидко спрацьовує DR1?

Залежить від типу тригера:
- **No-fix**: щонайменше 3 різні невалідні епохи за період не менше 600 мс
- **Мало супутників**: 3 різні low-count епохи з інтервалом щонайменше
  200 мс, за peak count у ковзному вікні приблизно 3 секунди
- **Стрибок позиції**: одразу при виявленні
- **EKF-тригер**: кожна bad category, включно з `GPS_GLITCHING` і post-healthy
  `UNINITIALIZED`, потребує щонайменше 2 нові декодовані reports за повний
  `EKF_TRIPMS`; default обох released targets — 500 мс, а tune у zero все одно
  зберігає мінімум 2 reports
- **SNR-аномалія**: після утримання `SNR_HOLDMS`

Див. [Тюнінг](#tuning) для налаштування цих порогів.

### Як літак повертається до GPS після DR1?

Фільтр перевіряє:
1. Кількість супутників >= `RJ_MIN_SATS`
2. HDOP <= `RJ_MAX_HD`
3. Умови виконуються протягом `RJ_STAB_MS`
4. Минув мінімальний час DR1 `DR_LOCK_MS`
5. На H743 проходить незалежний multi-evidence recovery quorum

Коли всі умови виконані, відновлюється DR0 і GPS-дані знову передаються. Див. [Тюнінг](#tuning) для деталей кожного параметра.

Legacy-параметри `RJ_REQEKF` і `EKF_OKRJMS` збережено лише для сумісності
схеми. F401 v1.6.26+ та H743 v0.5.5+ повертають для них нуль і ігнорують
writes, зокрема ненульові значення зі старих releases; вони не керують recovery.

### Що відбувається, якщо літак втрачає GPS надовго?

FC використовує dead-reckoning (IMU + компас + датчик швидкості). DR накопичує
дрейф з часом, тому літак має бути налаштований на повернення додому або
кружляння при втраті GPS. Фільтр має watchdog відновлення GNSS, який
надсилає команди гарячого/холодного перезапуску приймачу.

### Чи можна бачити, що робить фільтр під час польоту?

Так. Фільтр надсилає статусні повідомлення через MAVLink кожні 10 секунд
(налаштовується через `LOG_MS`). У вкладці Messages Mission Planner ви побачите:
- Зведення GNSS: `data=... fix=... nav=... SATS=... SNR=...`
- Режим/стан: `ARM=... DR=... BLEND=... LAT=... LONG=...`

На H743 DroneCAN `v0.2.0+` status і logging ідуть через S2/index `1`.
Налаштуйте цей virtual port для `STATUSTEXT`/`NAMED_VALUE` і зворотної FC
telemetry. Onboard screen (`PUB`, `WHY`, CAN counters, arm/safety bits) та
DroneCAN node status лишаються додатковими засобами перевірки. Camera S1/index
`0` і filter S2/index `1` працюють також у DR1.

Див. [Швидка довідка](#cheat-sheet) для швидкого пояснення цих повідомлень.

### Де завантажити плагін і пакет параметрів Mission Planner?

Завантажте [AirDroper Mission Planner Mod](https://gps.airdroper.org/download/mission-planner-mod). Він встановлює плагін карти телеметрії спуфінгу, описи й готові `.param` пресети для STM32-фільтра та flight controller. Закрийте Mission Planner перед запуском інсталятора, потім відкрийте його знову й оновіть список параметрів. Для live червоної/помаранчевої позицій і intersection трьох осей потрібне друге direct USB-C до H743; відкрита фіолетова RF-вісь працює через normal FC telemetry.

### Що робить пін B5?

Він видає імпульс високого рівня тривалістю 3 секунди при кожному переході DR0→DR1. Ви можете
підключити до нього світлодіод, зумер або зовнішній логер для фізичної
індикації активації захисного режиму. Див. [Схема підключення](#wiring) для деталей підключення.

### Що таке оцінка достовірності спуфінгу (DR_CONF)?

Починаючи з v1.5.5, фільтр обчислює бал 0–100 з до 10 різних рядків evidence.
Вищий бал = більше ознак спуфінгу. Лише receiver verdict `SEC-SIG` і
barometric vertical-rate row незалежні від сформованого атакувальником GNSS
content. Бал передається
як `DR_CONF` у телеметрії MAVLink і записується в кожен лог подій.

| Сигнал | Вага | Доступність |
|--------|------|-------------|
| Розходження vertical rate баро та GNSS | 20 | DroneCAN build зі свіжими FC barometer telemetry та GNSS vertical velocity |
| Аномалія SNR span | 20 | Усі підтримувані режими зі свіжим SNR/C/N0 |
| Receiver spoof verdict (`SEC-SIG`) | 25 | Лише H743 з підтримуваним u-blox |
| Стандартне відхилення pseudorange | 15 | Лише u-blox `NAV-SAT` |
| SNR temporal correlation | 12 | u-blox, partial passive NMEA, Mosaic SBF |
| Розворот курсу | 12 | Усі підтримувані режими |
| Різка зміна GDOP | 8 | Лише u-blox `NAV-DOP` |
| GPS time sanity | 12 | Усі підтримувані режими |
| Velocity-position consistency | 10 | Усі; partial на passive NMEA |
| Clock bias jump | 11 | u-blox і Mosaic SBF |

Бал автоматично адаптується: недоступні через target, transport або protocol
рядки виключаються зі зваженого середнього.

### Чи всі функції виявлення працюють з NMEA-приймачами?

Більшість функцій працює з u-blox і приймачами з пасивним NMEA, такими як
UM980/UM981/UM982 і Mosaic X5. Три advanced rows використовують UBX binary:

- **Аналіз pseudorange residual** (з NAV-SAT)
- **Виявлення різкої зміни GDOP** (з NAV-DOP)
- **Виявлення стрибку тактового зсуву** (з NAV-CLOCK)

H743 DroneCAN Mosaic SBF повертає binary C/N0 temporal і clock-bias coverage,
але не pseudorange residual або GDOP-jump confidence scoring.

Receiver-spoof verdict — окремий H743-only рядок `SEC-SIG`, тому він потребує
підтримуваний u-blox. Barometric vertical-rate divergence — рядок лише для
DroneCAN build; він натомість потребує свіжої FC barometer telemetry і GNSS
vertical velocity незалежно від протоколу приймача.

Основний захист (стрибок позиції, висота, SNR, курс, час, гео-огорожа)
працює з обома класами приймачів.

### Що таке DR1_MAXMS та FENCE_RAD?

- **DR1_MAXMS**: Примусовий вихід з DR1 після вказаної кількості мілісекунд.
  `0` = вимкнено. Корисно для місій, де нескінченне блокування GPS гірше за невизначений GPS.
- **FENCE_RAD**: Тригер DR1 при виході позиції за радіус від першого фіксу
  (макс. 2 000 000 м = 2000 км). За замовчуванням `0` (вимкнено) — вмикається
  встановленням ненульового радіуса. Виявляє повільний дрейф позиції при спуфінгу.

### Чи можна експортувати події в Google Earth?

Так, через dataflash-лог польотного контролера. Дістаньте `.bin`-лог із
SD-карти FC (або завантажте через MAVFTP), відкрийте у **Mission Planner** →
*DataFlash Logs* → *Review a Log*, далі *File* → *Create KML+GPX* для
експорту треку польоту. Рядки `MSG`, що починаються з `GNSS:` або `DR1:`,
позначають події спуфінгу вздовж треку, а записи `NVLI` `DR_CONF` містять
бал достовірності кожної події. Сама плата фільтра **не зберігає жодних
логів спуфінгу** — dataflash на SD-карті FC є єдиним джерелом істини
(EEPROM-кільцевий буфер на платі видалено у v1.6.8).

## Специфіка UM980

### UM980 показує червону швидкість/позицію в Mission Planner

Найімовірніші причини:
1. **`GPS_AUTO_CONFIG` увімкнений** (за замовчуванням) — ArduPilot перезаписує вашу
   конфігурацію UM980 на `MODE MOVINGBASE`, що некоректно для одноантенного
   БПЛА. Встановіть `GPS_AUTO_CONFIG=0`.
2. **Відсутній `MODE ROVER UAV`** у конфігурації UM980 — застосуйте повний профіль
   з [Конфігурації приймача](#receiver-config).

### Які повідомлення ArduPilot потребує від UM980?

Лише три: **GNGGA**, **GNRMC** та **AGRICA** — всі на частоті 5 Гц (період 0.2).
Драйвер ArduPilot не розбирає GPGSA, GPGSV, GPGST або UM980 binary
diagnostics. Парсер STM32 окремий: він розбирає GGA/RMC, ігнорує AGRICA та
proprietary binary diagnostics і може опційно розбирати GSV для SNR.
Тому задокументований GGA/RMC/AGRICA deployment profile показує `SNR=NA`;
optional GSV дає додаткове evidence і не потрібен для recovery з DR1.

### Чи потрібно налаштовувати UM980 при кожному увімкненні?

Ні. Команда `SAVECONFIG` наприкінці профілю UPrecise зберігає
все до енергонезалежної флеш-пам'яті UM980. Налаштуйте один раз — літайте завжди.

### Чи можна встановити прошивку самостійно?

Так. Придбайте ліцензійний ключ у [магазині](https://airdroper.org/products/gps-spoofing-filter) та слідуйте [Самостійній установці](#self-install). Для F401 усі операції — початкова активація, оновлення прошивки та відновлення — використовують **той самий ST-Link V2 адаптер (~$3)**, підключений до 4-пінного SWD-роз'єму (3V3, GND, A14/SWCLK, A13/SWDIO). **F401 BlackPill не має робочого USB-шляху** — ніколи не підключайте жодного кабелю до USB-C роз'єму BlackPill, включно з кабелем живлення. PA11/PA12 (по яких іде GPS UART до FC) фізично спільні з USB D-/D+, і будь-яке USB-сигналізування хоста блокуватиме передачу GPS до польотного контролера. Для H743 DroneCAN використовуйте target-aware CLI (`--target h743_dronecan`) або H743 USB-C ROM DFU шлях з [H743 DroneCAN Guide](13_h743_dronecan.md).

### Чи можна використовувати ліцензію на кількох платах?

Ні. Кожний ліцензійний ключ активує **одну плату**. Прошивка прив'язана до
унікального апаратного ID цієї плати.

### Як оновити прошивку?

Для F401 підключіть ST-Link V2 до 4-пінного SWD-роз'єму (3V3 → 3V3, GND → GND, SWCLK → A14, SWDIO → A13), відкрийте додаток **AirDroper GNSS Filter**, введіть ліцензійний ключ, перевірте active qualified firmware для вибраного board target і натисніть **Update / Оновити**. Inactive candidates і revoked releases застосунок не пропонує. Додаток автоматично знімає RDP, прошиває плату та повторно вмикає захист. H743 DroneCAN оновлюйте через `gnss-provision update --target h743_dronecan --stlink ...` або desktop app `2026.08.02.1+` з **Update transport -> USB-C ROM DFU**. Для RDP0 і RDP1 він перевіряє RDP, завжди виконує mass erase та повний rewrite перевіреного app+metadata+bootloader, а потім окремо підтверджує фінальний RDP1. Для RDP1 також потрібні UID-short confirmation, перевірка RDP0 після unlock і фізичне повторне читання UID. Без успішного читання option bytes і підтвердженого RDP1 застосунок не повідомляє про успіх. Див. розділ оновлення в [Самостійній установці](#self-install) і [H743 DroneCAN Guide](13_h743_dronecan.md).

### Чи можна перепровізіонувати плату, яка вже має прошивку?

Якщо плата вже має RDP1 (захист від зчитування), спочатку потрібно його зняти — це стирає flash. Підключіть **ST-Link адаптер** ($3-5) через SWD — інструмент прошивки зніме RDP автоматично.

### Як завантажити логи спуфінгу?

Логи спуфінгу більше не вивантажуються з плати фільтра. Кожна подія виявлення надсилається як MAVLink-повідомлення **STATUSTEXT** і **NAMED_VALUE_INT**, які ArduPilot записує на SD-карту контролера польоту як стандартні dataflash-записи `MSG` і `NVLI`. H743 DroneCAN `v0.2.0+` передає ці повідомлення через S2/index `1`. Дістаньте `.bin`-лог із SD-карти (або завантажте його через MAVFTP / Mission Planner) і перегляньте у Mission Planner чи [UAV Log Viewer](https://plot.ardupilot.org). Див. розділ логів у [Самостійній установці](#self-install).

### Що робити, якщо плата вийшла з ладу?

Зверніться до служби підтримки. Ми можемо деактивувати UID старої плати, щоб ви могли
використати ту саму ліцензію на новій платі.

### Чи може хтось вкрасти мою прошивку?

RDP Level 1 змушує звичайну спробу зчитування через debug port викликати mass
erase, а production app підписаний і прив'язаний до повного hardware UID
плати. Encrypted update packages також device-specific там, де цей update path
підтримується. Це fail-closed блокує звичайне extraction/copying і ускладнює
аналіз, але не робить advanced physical reverse engineering неможливим.

## Оцінка витрати палива

### Чи може фільтр сказати, скільки палива в мене лишилося?

Може оцінити — починаючи з H743 DroneCAN `v0.5.28+`. Він обчислює, скільки
потужності мусить поглинати ваш гвинт, за обертами двигуна, які польотний
контролер і так надсилає, і повідомляє це ArduPilot як пристрій EFI — тож
показник з'являється в наземній станції та в логах без додаткового датчика й
без додаткової проводки.

Це оцінка, а не вимірювання. У цьому тракті немає ні витратоміра, ні датчика в
баку. На літаку без покажчика палива вона буде єдиною індикацією палива, тому
її свідомо побудовано ЗАВИЩУВАТИ, а не занижувати, і вона лишається
орієнтовною, доки ви не скалібруєте її за одним зваженим польотом. Див.
«Калібрування оцінки витрати палива» в [Налаштуванні](06_tuning.md).

### Чому показник палива значно завищений?

Бо так і має бути до калібрування. Без калібрування він читає приблизно в
1.2–2 рази більше — це закладено навмисно: коефіцієнт гвинта несе запас, бо
заниження витрати зупиняє двигун, а завищення лише садить вас раніше. Один
зважений політ і одне значення `FUEL_TRIM` доводять похибку до 10–20%.
Очікуйте значення приблизно 0.5–0.9.

### Підсумок палива не обнулився після заправки

Запишіть `FUEL_CAPG`. Це єдине, що обнуляє накопичений підсумок, і так
задумано: підсумок тепер переживає перезавантаження в польоті, тож він не може
водночас скидатися сам щоразу, коли плата перезапускається. Записуйте його
після кожної заправки, навіть якщо розмір баку не змінився. Ви побачите
`FUEL_CAPG written - fuel total zeroed`. Запис приймається лише після fresh
stopped-engine quorum: disarmed, valid zero RPM і closed throttle. Якщо числова
місткість змінилася, це повідомлення підтверджує лише runtime reset: EFI
лишається silent, доки asynchronous save journal не повідомить `Tune saved`.
`Tune save failed` лишає total LOST і не є відновленням.

Встановлюйте `FUEL_DENS` до `FUEL_CAPG`. Запис густини потребує того самого
fresh stopped-engine quorum. Фактична зміна позначає total як LOST, скасовує
старий pending capacity commit і блокує записи місткості з
`FUEL_CAPG blocked: wait for FUEL_DENS save` до verified save density journal. Failed save лишається
blocked/LOST. `Tune saved` знімає цей block, але не відновлює EFI; потім
наступний stopped-quorum запис `FUEL_CAPG` встановлює fresh zero.

### Що стається при втраті телеметрії FC або збереженого fuel total?

Облік палива триває крізь втрату FC-link і FC-version output block. Кожен boot
починається з установленим консервативним engine-may-be-running latch; тиша
лінку не скидає його, а відсутні RPM нараховуються за номінальною потужністю,
доки одночасно fresh disarmed state, valid zero RPM і closed throttle не
підтвердять зупинку. Запис `FUEL_CAPG` приймається лише після того, як ці самі
три inputs стали fresh; сам запис не очищає цей engine latch.

Якщо при будь-якому boot немає надійного V2 backup record (зокрема при
звичайному вмиканні, warm reset або legacy V1 record), total невідомий і фільтр
взагалі не надсилає DroneCAN ICE Status. Такий самий fail-closed результат діє,
коли H743 tune journal відсутній, пошкоджений або не має valid record: surviving
numeric total не можна довіряти, якщо provenance settings місткості, густини й
моделі, за яких він накопичувався, невідомий. POR/PDR не доводить заправку. EFI
backend ArduPilot стає stale/unhealthy замість прийняти хибний нуль. Кожні 60 с
фільтр повторює `Fuel total LOST - write FUEL_CAPG to restart it`. Сідайте або
лишайтеся на землі, перевірте fuel configuration, дочекайтеся fresh
stopped-engine quorum (disarmed + valid zero RPM + closed throttle) і повторно
запишіть `FUEL_CAPG` для палива на борту, навіть якщо його числове значення не
змінилося. Змінене значення очистить lockout лише після `Tune saved`; disarmed
alone відхиляється. Valid restore також отримує обмежене консервативне
25-секундне reset-gap нарахування за номінальною потужністю; це не точне
вимірювання витрати під час reset/startup. Прийнятий запис, що встановлює новий
total, скасовує pending charge старого відновленого total.

Спроба factory reset записує TOTAL LOST у BKPSRAM до початку flash work. Тому
навіть failed attempt може консервативно лишити EFI silent. Після будь-якої
спроби перевірте всі settings fuel model і виконайте stopped-engine recovery
через `FUEL_CAPG`; якщо місткість змінилася, дочекайтеся `Tune saved`.

### Що означає `Fuel held up by throttle - check RPM_SCALING`?

Положення газу передбачає більшу потужність, ніж показання обертів, тож фільтр
підпирає оцінку замість того, щоб повірити підозріло низьким обертам. Звична
причина — `RPM1_SCALING`, налаштований на хибну кількість імпульсів на оберт:
здвоєний CDI дає два, а налаштування на один зменшує кожне показання вдвічі.

**Звірте це з ручним тахометром, перш ніж летіти знову.** У фільтра одне
джерело обертів, тож більше ніщо на літаку цього не виявить.

## Пошук джерела перешкод

### Чи можу я дізнатися, де стоїть глушилка?

Приблизно. Починаючи з `v0.5.27+` фільтр видає й логує радіовимірювання,
потрібні для оцінки пеленга. Mission Planner plugin `v0.3.0+` показує
provisional live двосторонню вісь; після польоту виконайте
`python tools/df_analyze.py flight.bin` на лозі польотного контролера. Коли fit
відповідає, очікувана точність — приблизно ±20–45°, але показаний fit sigma не
враховує age курсу FC.

Щоб це спрацювало, треба **пролетіти повне коло** крізь зону завад. Метод
читає, як потужність завади змінюється з вашим курсом, тож прямий проліт не
дає йому нічого — і інструмент скаже вам про це, а не вгадуватиме.

Один пеленг — це вісь, а не позиція. Plugin `v0.3.0+` може показати фіолетовий
**UNVALIDATED advisory intersection**, але лише після трьох фіналізованих осей
із рознесених точок. Вимога трьох осей дозволяє відкинути несумісний segment;
будь-які дві непаралельні математичні лінії завжди нібито перетинаються. Доки
полярність не звірено з контрольованим передавачем, вважайте кожний пеленг
лінією, а не стрілкою.

Live plugin потребує щонайменше 20 samples і справжнього розвороту: 90° —
мінімум, повне коло краще. Замість вгадування він показує `COLLECTING` або
`ABSTAIN`. RF-вісь надходить через звичайну телеметрію FC. Для source
intersection потрібен private USB: кожна збережена вісь прив'язується до
рухомої DR reference, а керована атакувальником червона позиція ніколи не є
anchor. Збережіть три кваліфіковані segments тривалістю 20–120 секунд у межах
трьох хвилин: **кожна пара** anchors має бути рознесена щонайменше на 500 м, а
кожна пара axis directions — мінімум на 30°. Остання
вісь stale через 30 секунд. Фіолетова мішень і коло sensitivity припускають
одне нерухоме джерело; це не ground truth, accuracy radius або waypoint.

Ніщо з цього не повертається у виявлення спуфінгу чи керування літаком.
Firmware лише видає/логує observables; fit виконує GCS або offline tool.

## Карта РЕБ перешкод

### Що таке карта РЕБ перешкод?

Це жива веб-карта на [gps.airdroper.org/ew-map](https://gps.airdroper.org/ew-map), яка показує глобальні GNSS перешкоди в реальному часі. Вона об'єднує дані з кількох джерел:

- **Авіаційні ADS-B дані** (OpenSky) — виявляє перешкоди порівнянням барометричної та GPS висоти по 5 регіонах світу
- **Морські AIS дані** — виявляє судна з збоями GPS у Балтиці та за її межами
- **Повітряні тривоги України** — статус тривог по областях у реальному часі
- **61 відома зона РЕБ** — статичні військові зони перешкод по всьому світу з перехресним підтвердженням живими даними
- **Конфліктні події GDELT** — свіжі сигнали конфліктів, які можуть корелювати з активністю РЕБ
- **Теплові аномалії NASA FIRMS** — пожежні й теплові виявлення, що допомагають підтвердити активні зони ризику
- **Краудсорсингові звіти** — повідомлення користувачів про перешкоди

Карта безкоштовна і не потребує входу в систему.

### Чи можна вбудувати карту РЕБ на свій сайт?

Так. Використовуйте віджет `gps.airdroper.org/ew-map/embed` в iframe:
```html
<iframe src="https://gps.airdroper.org/ew-map/embed" width="100%" height="500"></iframe>
```

### Чи можна отримувати сповіщення про перешкоди?

Так, три способи:
1. **Email/webhook** — підпишіться внизу сторінки карти РЕБ або через `POST /api/v1/ew-map/subscribe`
2. **Telegram** — напишіть боту команду `/subscribe`
3. **Публічний API** — зареєструйте безкоштовний API-ключ через `POST /api/v1/ew-map/register-key` (100 запитів/день)

### Чи можна перевірити ризик перешкод для маршруту?

Так. Використовуйте API оцінки ризику маршруту:
```
POST https://gps.airdroper.org/api/v1/ew-map/route-check
Body: {"waypoints": [[lat1, lon1], [lat2, lon2], ...]}
```
Повертає оцінку ризику (0–100) для кожного сегменту на основі відомих зон, живих ADS-B даних та повітряних тривог.

### Чи прогнозує карта майбутні перешкоди?

Так. Сервер будує патерни ймовірності за часом доби на основі 7 днів історичних даних. Запитуйте прогнози через `GET /api/v1/ew-map/predictions/now`.
